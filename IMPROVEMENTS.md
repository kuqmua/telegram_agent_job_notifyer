# План Улучшения Кодовой Базы
## Цель
Сделать проект надежным для постоянной работы Telegram-бота, упростить поддержку, повысить предсказуемость поведения и подготовить код к расширению функционала.
## Текущее состояние
- Режим работы бота: `long polling` через `getUpdates`.
- Основная логика сосредоточена в `server/src/main.rs`.
- Базовые команды: `/health`, `/codex <prompt>`.
- Есть рабочий `README`, но пока нет системного плана по качеству, наблюдаемости и развитию.
## Приоритеты
1. Стабильность и отказоустойчивость polling.
2. Структура кода и границы модулей.
3. Покрытие тестами критического поведения.
4. Наблюдаемость и эксплуатация.
5. Безопасность и управление секретами.
6. Подготовка к функциональному росту.
## Этап 1. Декомпозиция `server/src/main.rs`
### Задачи
- Вынести Telegram polling в отдельный модуль: `server/src/telegram/polling.rs`.
- Вынести Telegram API клиентские функции в `server/src/telegram/api.rs`.
- Вынести обработку входящих команд в `server/src/telegram/commands.rs`.
- Вынести конфигурацию env в `server/src/config.rs`.
- Оставить в `main.rs` только инициализацию состояния, роутера и запуск фоновых задач.
### Критерии готовности
- `main.rs` не содержит бизнес-логики Telegram команд.
- Каждый модуль имеет 1 ответственность и минимальный публичный API.
- Поведение сервиса не изменилось.
## Этап 2. Устойчивость polling-цикла
### Задачи
- Добавить backoff стратегию при сетевых ошибках (`min/max delay` + jitter).
- Разделить типы ошибок на временные и постоянные.
- Ввести таймауты на внешние HTTP вызовы к Telegram.
- Добавить защиту от повторной обработки update (идемпотентность по `update_id` в runtime).
- Добавить ограничение длины исходящих сообщений и единый helper для chunking.
### Критерии готовности
- При сбоях сети сервис восстанавливается без ручного перезапуска.
- Нет штормов запросов к Telegram при ошибках.
- Длинные ответы доставляются предсказуемо.
## Этап 3. Команды и доменная модель
### Задачи
- Сделать явный enum для входящих команд: `Health`, `Codex(String)`, `Unknown`.
- Вынести парсинг текста команды в отдельную чистую функцию.
- Ввести единый формат системных сообщений бота.
- Добавить отказоустойчивую обработку пустых/битых апдейтов.
### Критерии готовности
- Обработка команды покрыта юнит-тестами без сетевых зависимостей.
- Любой входной текст приводит к детерминированному результату.
## Этап 4. Тесты
### Задачи
- Юнит-тесты для:
- парсинга команд;
- нормализации/обрезки ответа `codex`;
- преобразования Telegram update в внутреннюю модель;
- конфигурации env.
- Интеграционные тесты с mock HTTP сервером для Telegram API (без реального Telegram).
- Smoke-тест запуска сервера и проверки доступности `/health`.
### Критерии готовности
- Покрыты критические ветки ошибок и успеха.
- Тесты стабильно проходят локально и в CI.
- Нет зависимости от внешних сервисов в тестах.
## Этап 5. Наблюдаемость
### Задачи
- Стандартизировать structured logs (поля: `event`, `chat_id`, `update_id`, `command`, `duration_ms`, `status`).
- Добавить correlation-id для одной обработки команды.
- Вести отдельные логи для:
- получения update;
- начала/конца выполнения codex;
- отправки ответа в Telegram;
- ошибок внешних API.
- Добавить маршрут `GET /health/live` (жив процесс) и `GET /health/ready` (готовность обрабатывать polling).
### Критерии готовности
- По логам можно восстановить полный путь обработки сообщения.
- Есть четкое разделение liveness/readiness.
## Этап 6. Безопасность
### Задачи
- Убрать токены из репозитория и истории (ротация `TELEGRAM_BOT_TOKEN` обязательна).
- Добавить проверку на пустые/подозрительные env значения на старте.
- Убедиться, что токен никогда не попадает в логи.
- Добавить раздел в README по безопасной работе с `.env`.
### Критерии готовности
- Токен не экспонируется в коде, логах и документации.
- При неверной конфигурации сервер падает явно и понятно.
## Этап 7. Производительность и ресурсная модель
### Задачи
- Ограничить число параллельных `codex` задач (очередь или semaphore).
- Ввести таймаут выполнения `codex` команды.
- Добавить контроль размера stdout/stderr от `codex`.
- Проверить отсутствие лишних clone в горячем пути polling.
### Критерии готовности
- Сервер не деградирует при серии сообщений.
- Ограничены CPU/память при пиковых сценариях.
## Этап 8. Документация и DX
### Задачи
- Обновить `README.md` под актуальную архитектуру без webhook.
- Добавить `docs/architecture.md` с диаграммой потока update.
- Добавить `docs/runbook.md` для типовых инцидентов (`409`, rate limit, пустые updates).
- Добавить `make`/`just` команды для запуска, линтов и тестов.
### Критерии готовности
- Новый разработчик запускает сервис за 5-10 минут.
- Инциденты закрываются по runbook без чтения исходников.
## Этап 9. CI качество
### Задачи
- Зафиксировать pipeline: `fmt`, `clippy -D warnings`, `test`.
- Добавить проверку на утечку секретов.
- Добавить проверку изменения документации при архитектурных правках.
### Критерии готовности
- Любая деградация качества блокируется на CI.
- Основная ветка всегда в рабочем состоянии.
## Риски
- Изменение структуры модулей может временно усложнить отладку.
- Добавление ограничений на `codex` задачи может повлиять на UX.
- Неполное покрытие edge-cases Telegram update приведет к "тихим" потерям событий.
## Последовательность выполнения
1. Этап 1 (структура).
2. Этап 2 (устойчивость polling).
3. Этап 3 и 4 (модель команд и тесты).
4. Этап 5 (наблюдаемость).
5. Этап 6 (безопасность).
6. Этап 7 (производительность).
7. Этап 8 и 9 (документация и CI).
## Definition of Done
- Все этапы выше закрыты по критериям.
- `cargo fmt` и `cargo clippy --all-targets --all-features -- -D warnings` проходят.
- Тесты проходят стабильно.
- README и runbook отражают реальный запуск и эксплуатацию.
